写于重排代码和运行脚本之前，单独一次提交；提交时间就是登记时间。到这次提交为止，没有在这 47 题上调用过重排模型。
机器可读的版本是 [preregistered.json](preregistered.json)，之后提交的运行脚本读它，参数不一致就不跑。之后不改本文件，改动另起新版本并保留旧结果。

## 这套题在这次里的作用

重排有没有用，看真实年报那 40 题，登记在 [preparation/s4/real-reports/rerank](../../../s4/real-reports/rerank/PREREGISTRATION.md)。这 47 题不用来证明提升，只回答两件事：
加了重排，原来找得到的还找不找得到；权限链有没有因此放宽。

不拿它证明提升的原因：

- **这套题已经用过。** 词法基线、向量 / 混合对比都在它上面跑过，可回答性判断也拿它做过探索性对照；逐题结果早就看过。
- **重排在这里几乎没有发挥的余地。** 封存的混合检索运行里，47 题有 44 题返回的结果不到 5 条（0 条 10 题，1 条 18 题，2 条 9 题，3 条 7 题）：重排不设阈值、不删结果，这些题前 5 里有哪些文档不会变，只会变顺序。
  混合检索漏掉的两题（Q13、Q22）是目标的余弦相似度低于 0.50 下限，根本没进候选，重排救不回来。

## 固定不变的部分

- 题集、gold、评测器：`dataset.json`、`evaluator.py` 等冻结文件逐字节核对 `freeze.json`（sha256 `4b31cf95…`），不一致就不运行；评测器原样导入，每题重复 5 次，与冻结协议相同。
- 混合检索：`bge-m3`（本机 Ollama）、余弦下限 0.50、RRF k = 60、top_k = 5，与 [hybrid/PREREGISTRATION.md](../hybrid/PREREGISTRATION.md) 相同。
- 权限顺序：Store 先按角色、密级、scope 过滤 → 复核 → 混合检索排序 → 重排 → 逐条重新授权引用。`RankedKnowledgeService.search` 和 `_cited_hits` 不改，`context.py` 不动。
  **重排模型只拿到调用者有权读的内容**：测试对 47 题逐题核对送进重排模型的每一段文字，运行脚本再核对一遍并计数。

## 重排的设置

与年报那边登记的完全相同，两份 `preregistered.json` 里的 `reranker` 一段逐项一致，运行脚本会核对：

| 项 | 登记值 |
|---|---|
| 模型 | `BAAI/bge-reranker-v2-m3`，sentence-transformers 的 `CrossEncoder`，本机加载，`device='mps'`，float32 |
| 候选数 N | 混合检索排出的前 30 条；不足 30 条就全部重排 |
| 输入 | 问题原样；候选是 Store 里那一行的全文 |
| max_length | 1024 个 token |
| 分数 / 阈值 | 原始 logit，只用来排序；不设阈值，不删任何一条 |
| 同分 | 保持混合检索原来的先后 |
| 批大小 / top_k | 8 / 5 |

## 事先定下的护栏

加重排后的结果和封存的混合检索运行比，下面四条都满足才算护栏通过：

1. **越权为 0**：越权泄漏 0/47，越权候选与越权引用观测都为 0；送进重排模型的文字里，不在调用者可读范围内的为 0 条；
2. **找回不退步**：内容正例 Recall@5 不低于 93.33%（30 题），全部正例 Recall@5 不低于 94.59%（37 题）；
3. **精确词 / ID 题不退步**：该切片不低于 1/1；
4. **无答案题**：返回非空上下文的不多于 1/3。

护栏不通过，年报那边的结论就是“不采用”，不管年报题提升多少。
MRR@5（封存运行：全部正例 93.24%，内容正例 91.67%）、5 次重复是否一致、时延照实报告，不设门槛；MRR 比混合检索低的题逐题列出。

## 不能宣称的

- 护栏通过只说明在这组小的合成夹具上，重排没有丢掉原来找得到的来源、没有放宽权限；不说明重排有用。
- 26 条短文档，每题候选最多二十几条，离真实资料的候选规模很远；这里的时延不代表年报上的时延。
- 冲突检测（0/2）不是排序能解决的，照旧报告，不计入护栏。
