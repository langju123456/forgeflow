# 审阅人怎样判断改稿影响了哪些数字

场景是上次会议同时要增速和贡献，这次只留下贡献。审阅人想知道撤下了哪个指标、留下的结论是否仍用同一个分母、复核时要不要重新看原表。本轮由 Codex 代选、代跑，用户可依据实测重新选择。

|候选做法|使用体验与代价|
|---|---|
|1. 自己下载两版并打开|保留完整上下文，需要在窗口间找改动|
|2. 对照两段结论文字|一眼能看到措辞；引用变了而结论没变时会漏报|
|3. 比较 JSON 的全部叶节点和数组位置|字段覆盖广；任务 ID、时间和列表位移也进入结果|
|4. 按财务指标、期间、原格与来源标记新增、移除、改动|可区分撤掉指标及改动分母；需要明确定义支持的字段|
|5. 只用百分比差值设告警|查看快；不同分母也可能给出相同百分比|
|6. 在原 PDF 页面叠图|适合检查重新排版；说明和公式没有视觉坐标|
|7. 让模型撰写修改摘要|阅读顺畅；需核实它是否漏写移除项或自行解释原因|
|8. 用户填写强制修改说明|理由来自操作者；不能验证实际改动|
|9. 记录每个编辑按键并回放|适合查编辑过程；操作轨迹不直接表达最终口径|
|10. 为所有指标建立依赖图并标出受影响段落|适合多章报告；当前两个结构化查表尚无完整依赖图|

试验选择 2、3、4。每种做法读取同一对持久归档，各运行一次，预算均为零外部调用。用真实 Apple 两版验证撤项，补充明确标注为派生输入的对照，分别隔离分母、证据位置和运行元数据变化。以机械输出和具体漏项判断，人工节时需独立试用另测。

## 观察结果

|同一组输入|只对照结论句子|逐个 JSON 字段核对|按业务字段对照|
|---|---|---|---|
|公开归档，v2 只要贡献|两句消失、一句新增。保留的贡献句换到句首，带上了公司名|18 个字段位置不同，含公式列表移动和运行信息|移除服务收入增速；保留增长贡献。另有研究问题、结论文字及作者说明三处变化。两次引用均为原来的第 26、39 页|
|派生输入，仅将分母加一，维持显示百分比|没有变化|2 个字段变化，含版本号|列出贡献指标，旧分母 25,126，新分母 25,127|
|派生输入，原表一个坐标加一|没有变化|2 个字段变化，含版本号|第 26 页原表定位发生变化|
|派生输入，改版本及运行编号，内容相同|没有变化|2 个字段变化|零项业务变化|

Codex 建议在审阅页采用第 4 种，保留现有逐版原始 JSON 下载。指标通过名称配对，财年、单位、公式、分子、分母和显示百分比进入对照。金额按年份配对，原表按引用 ID 核对文件、页码、坐标、原格版本、内容指纹和摘录。金额和百分比以归档值为准；此功能展示变化，正确性仍需对照原表。十个方案中仅第 2、3、4 项做了本轮实验。时间戳与查询任务号可在原始归档中查到。

## 复现与可见范围

在仓库根目录运行 `web/node_modules/.bin/vite-node scripts/revision_diff_dev.mjs`。输出保留输入文件哈希、每种方法逐项输出及派生输入标记。[原始对照输出](revision-diff-dev.json)

实时 Chrome 验收另起临时研究库，用之前已核验的 Apple PDF 和本机解析缓存发起实际查询。两个浏览器分别持有研究员和审阅人本机凭证。v1 同时报增速和贡献，审阅人退回。研究员先存 v2 私稿，再查贡献、修成 v3 并送审。研究员可看 v2 → v3；审阅人看到 v1 → v3 及 v1 的退回意见。记录浏览器请求确认审阅人仅取 v1 的历史归档。v3 随后成功获批并登记本地交付。两种身份均由脚本操作，全程无模型调用。[审阅人实际界面](revision-diff-ui.png)

目前适配 Apple 结构化计算和共有的结论、注释、来源及摘录。宁德时代早期稿件的现金流金额保存在正文和原表摘录中；独立的现金流结构化金额差值仍待实现。对多章节报告的变更传播和真实用户节时尚待验证。
